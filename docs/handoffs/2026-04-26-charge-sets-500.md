# Handoff — `Failed to load charge sets` 500 on Load Detail → Billing tab

**Symptom:** Opening any load → Billing tab shows red banner "Failed to load charge sets". Network shows `GET /api/tenant/loads/<order_id>/charge-sets` returning 500. Reproducible on `TEST-M000022` (just-created via the new NewLoadModal) AND on at least one other load id (`eeea71b7-3c56-40d4-a6a1-4f0fc85fca9f`) — so this is **NOT specific to loads created via the redesigned modal**. Likely pre-existing, surfaced by spot-checking after the modal redesign shipped.

**Surfaced:** 2026-04-26 by user spot-checking the just-shipped NewLoadModal redesign (`0803740`).

## Root cause (already diagnosed)

The endpoint at [pages/api/tenant/loads/[id]/charge-sets/index.js:32-48](../../pages/api/tenant/loads/[id]/charge-sets/index.js) runs:

```js
.from('order_charge_sets')
.select(`*,
  bill_to:customers!order_charge_sets_bill_to_customer_id_fkey(...),
  line_items:order_charge_set_line_items(*),
  invoice:invoices!invoice_id(...)`)
```

The `invoice:invoices!invoice_id(...)` join asks PostgREST to follow a foreign key from `order_charge_sets.invoice_id → invoices.id`. **But that FK doesn't exist in the schema.**

Reproduction with service role:
```
error: Could not find a relationship between 'order_charge_sets' and 'invoices' in the schema cache
data length: 0
```

**Why no FK:** Looking at [supabase/migrations/003_phase5b1_loads.sql:171](../../supabase/migrations/003_phase5b1_loads.sql), the `order_charge_sets.invoice_id` column was created as a plain `UUID` with no `REFERENCES invoices(id)` constraint. The `invoices` table didn't exist yet at migration 003 — it landed in 042 (`042_invoice_numbers.sql`) — and no later migration added the FK retroactively. Verified via grep across all migrations: no `ADD CONSTRAINT order_charge_sets_invoice_id_fkey` exists.

## Two fix paths

### Option A (recommended): Add the missing FK

New migration `106_order_charge_sets_invoice_fk.sql`:

```sql
BEGIN;

-- Add the FK that's been missing since migration 003. SET NULL on invoice
-- delete because charge sets can outlive their invoice (rebill scenarios
-- already use rebilled_to_invoice_id / rebilled_from_invoice_id from
-- migration 095).
ALTER TABLE order_charge_sets
  ADD CONSTRAINT order_charge_sets_invoice_id_fkey
  FOREIGN KEY (invoice_id) REFERENCES invoices(id) ON DELETE SET NULL;

NOTIFY pgrst, 'reload schema';

COMMIT;
```

Pros: minimal, semantically correct, fixes all consumers of the API endpoint at once.
Risks: if any rows in production have `invoice_id` pointing to a non-existent invoice, the ALTER will fail. Mitigation: pre-check `SELECT count(*) FROM order_charge_sets WHERE invoice_id IS NOT NULL AND invoice_id NOT IN (SELECT id FROM invoices);` — should be 0; if nonzero, NULL them first or investigate orphans.

### Option B: rewrite the query

Replace the PostgREST nested join with two separate queries — fetch charge sets, then fetch invoices for the non-null invoice_ids in a separate `.in()` call, then merge in JS. More code, no schema change. Use only if Option A's ALTER fails on production data and the orphan situation is too messy to clean up.
